## 1. 结论

当前版本虽然使用原创名称和美术，但可见对象和操作仍完整呈现“手中持有一组牌、逐张出牌、比较结果、累计胜负单元”的结构。仅替换卡面、花色图标或术语，不能形成可信的非牌类产品。

本方案不以“规避识别”为目标，而是把实际可玩产品改造成一套非牌类玩法：保留“先定目标、争夺公共机会、达到目标后主动避让、按准确度结算”的体验循环，同时删除牌、牌组、手牌、发牌、花色、点数、王牌、跟牌、出牌和赢墩等对象与交互。

第一阶段只制作审核证据链所需的视觉方案和真实本地 Cocos 可玩切片。只有当陌生用户盲测及平台人工咨询均支持“非牌类”理解后，才进入全量规则、协议、服务器和好友房迁移。

## 2. 改造目标与边界

### 目标

- 普通观察者在 10 秒内把玩法描述为“移动、换轨、抢收集物、控制数量或节奏”，而不是牌类玩法。
- 一段连续实机视频能够证明核心交互是实时移动与路径选择，不依赖说明文案掩盖旧玩法。
- 截图、规则页、分享图、商店资料、运行时资源和实际行为互相一致。
- 在投入联网重构前，用低成本切片验证新的产品理解是否成立。

### 第一阶段明确不做

- 不修改好友房协议、Cloud Hosting 服务、Redis 房间数据或断线恢复协议。
- 不迁移正式联网对局，不兼容新旧玩法跨版本联机。
- 不把视觉概念稿直接当作提交版本。
- 不承诺审核结果；类目与资质要求最终以微信平台实际反馈为准。

## 3. 保留什么，真正删除什么

| 原体验价值 | 新实现 | 对外可见结果 |
| --- | --- | --- |
| 开局先判断局势并设定精确目标 | 观察双环路线、桥位和首批茶灵分布后选择本轮接取目标 | “选目标”，但没有叫牌或牌面信息 |
| 多人争夺有限公共机会 | 多名旅客在同一连续路线实时移动，先经过茶灵者完成接取 | 路径、速度和时机竞争 |
| 达到目标后要主动规避额外收益 | 达标后通过减速、加速或预备换轨绕开后续茶灵 | 可直接看到“躲开多余收集物” |
| 结果取决于是否准确完成目标 | 回合结束比较目标数与实际接取数 | 准确度结算得到保留 |
| 多轮累计排名 | 多次巡游累计分数 | 保留好友间的轻竞技结构 |

必须从正式产品中删除的旧结构包括：私人手牌区、公共牌堆、发牌动画、统一卡片矩形、牌背扇形排列、点数与花色体系、王牌状态、轮流出牌、跟牌限制、中央一墩和牌类规则文案。删除范围最终包含隐藏入口、练习模式、恢复会话、远程开关和安装包内资源，不能只隐藏首屏。

## 4. 新玩法：巡香接露

### 4.1 场景与对象

- 场景是一张漆木茶台上的两条连续同心巡游路线。
- 内外环之间设六处明确可读的连接桥。
- 每位玩家控制一名持续前进的动物旅客，旅客携带可见的接露托盘。
- 茶灵会在路线节点出现；最先经过该节点的旅客接取茶灵。
- 第一切片只使用一种、同价值茶灵，避免形成可被理解为花色或牌面层级的分类系统。

### 4.2 单回合流程

1. **观察（5 秒）**：展示双环路线、六座桥和首批茶灵位置。
2. **定标（8 秒）**：玩家选择本轮希望接取的茶灵数量。
3. **巡游（60 秒）**：所有旅客同时自动前进，玩家实时调整速度和路线。
4. **结算**：显示“目标 / 实际 / 偏差 / 本轮得分”，随后进入排名。

### 4.3 玩家操作

- `减速`：把当前速度降低一级。
- `预备换轨`：在下一座连接桥自动切换内外环；再次点击可取消。
- `加速`：把当前速度提高一级。

三项操作始终位于底部操作带。玩家角色、运动方向、下一桥位、预备换轨状态和速度档位必须直接可见。游戏采用同时行动，不出现“等待某人出牌”式的离散回合。

### 4.4 最小计分规则

- 实际接取数等于目标数：`+20`。
- 未命中目标：`-5 × 绝对偏差`。
- 本地切片完成一轮后直接展示结果；多轮累计规则留到验证通过后再定稿。

计分数值是切片参数，不构成正式平衡承诺。第一阶段验证重点是产品类型理解和操作闭环。

## 5. 审核者会看到的六个表面

### 首页

- 产品名与主题改为“奇术茶馆·巡香接露”。
- 保留创建房间、加入房间和单人练习入口。
- 主视觉表现旅客沿发光茶路巡游和接取茶灵，不出现牌或类似手牌的装饰构图。

### 好友房大厅

- 座位、准备、AI 补位和邀请关系可保留。
- 模式说明改为巡游时长、轮数和是否启用计时，不出现牌局参数。

### 目标选择

- 独立展示路线与首批茶灵分布。
- 使用数量刻度或圆形拨盘选择目标，不使用横排矩形选择牌。

### 核心玩法

- 画面主体始终是连续运动的双环路线、连接桥、旅客和茶灵。
- 固定 HUD 为 `本轮目标 4 / 已接 3 / 还差 1`。
- 底部固定显示 `减速 / 预备换轨 / 加速`，并提供即时运动反馈。

### 结果页

- 每行只展示头像、目标、实际、偏差和得分。
- 使用路线轨迹或接露托盘作为回顾视觉，不复用旧牌桌或卡片缩略图。

### 分享封面与后台资料

- 分享图表现多人巡游和接取动作。
- 简介、玩法说明、截图和视频统一使用“实时路径选择与数量控制”的事实描述。

## 6. 第一阶段实施范围

### 阶段 A：三套核心玩法视觉方向（已完成选型）

三套方案必须呈现完全相同的玩法对象和操作，只探索不同的信息层级与镜头组织：

- **漆环巡游**：近俯视完整双环，路线是绝对主角，三项操作形成底部仪表带。
- **月台逐香**：斜俯视强化旅客运动和前方机会，目标信息集中在一侧。
- **灯河换径**：墨色茶台上以发光流线突出路线与桥门，HUD 嵌入灯笼和卷轴层级。

共同硬约束：横版 16:9；延续暖漆、纸卷、灯笼、墨洗夜景和动物旅客；不出现任何牌、牌背、牌堆、手牌扇形、花色、点数或中央出牌区。

2026-08-21 已选定 **漆环巡游**，视觉真值保存为 [`art/mockups/patrol-gameplay-screen-v1.png`](../art/mockups/patrol-gameplay-screen-v1.png)。后续 Cocos 切片以该图的布局、组件结构、密度、间距、色彩、字体、可见内容和层级为准。

### 阶段 B：真实本地 Cocos 可玩切片

切片范围固定为：

- 1 名真人 + 2 名 AI；
- 1 张双环路线、6 座连接桥；
- 1 种同价值茶灵；
- 观察、定标、60 秒巡游、结果四个阶段；
- 三项玩家操作及可读的速度、路线和换轨反馈；
- 一轮结束后的目标准确度结算。

实现要求：

- 新规则仍放在 `packages/game-core`，平台输入、Cocos 节点和微信 API 不进入纯规则层。
- 切片使用独立启动入口和独立本地会话，不接入现有房间协议。
- 画面必须由运行时对象驱动，不能用整张概念图加热点伪装交互。
- 所有 Cocos 可见资源通过 `art/asset-manifest.json` 和 `npm run cocos:sync` 管理，不手改生成地址文件。

### 阶段 C：理解度盲测

邀请 5 名未参与项目的人，先看 10 秒静态画面，再观看 30 秒无解说操作。只问：

1. “这是什么类型的游戏？”
2. “玩家主要在做什么？”
3. “画面里哪些对象决定输赢？”

通过条件：

- 5/5 不把它描述为纸牌、扑克、卡牌或出牌游戏；
- 至少 4/5 主动提到移动、路线、换轨、时机、抢占或控制收集数量；
- 至少 4/5 能正确指出“目标数与实际接取数的差”决定结果。

不向参与者解释“我们希望它不是牌类”，避免诱导答案。

### 阶段 D：审核咨询证据包

在正式全量迁移前准备：

- 80 秒左右连续、无剪辑的 Cocos 实机视频：进入练习 → 观察 → 定标 → 实时巡游 → 结果；
- 首页、目标选择、玩法中、结果页四张一致截图；
- 一页玩法事实说明，列出游戏对象、输入方式、胜负条件和不存在的牌类结构；
- 与构建一致的名称、简介、规则页和分享图草案。

将该证据包提交微信开发者助手或相应人工渠道，询问应选择的实际类目与所需资质。收到明确反馈前，不启动正式联网迁移。

## 7. 后续全量迁移的启动条件

只有同时满足以下条件，才进入第二阶段：

- 三套视觉方向已选定并通过内部可读性检查；
- 本地切片能在 Cocos `wechatgame` 构建中完整完成一轮；
- 盲测达到上述门槛；
- 平台人工反馈没有继续把展示版本直接归为牌类，或给出了可执行的非牌类申报路径；
- 团队接受旧玩法与新玩法不能在同一提交包中共存。

第二阶段才处理：正式多轮规则、3–6 人平衡、好友房协议 v2、权威服务、AI、断线恢复、分享直入、完整资源替换、旧资源清理和最终微信真机验收。

## 8. 停止条件与回退

出现任一情况，应停止继续投入全量重构：

- 盲测仍普遍把核心玩法理解为换皮牌类；
- 为保留旧规则而不得不恢复手牌、逐张选择、花色比较或离散轮流行动；
- 平台基于实机证据仍明确要求按牌类或内购游戏资质流程办理；
- 新玩法不能在本地切片中形成独立、可理解且有策略性的 60 秒闭环。

停止后可选择按平台要求准备游戏资质，或另立真正不同的休闲玩法项目；不得继续通过隐藏入口、改词或只换美术反复提交。
